ВышКат — система учёта транспорта

Учебное консольное приложение на Go для учёта объектов транспортного парка. Программа позволяет принимать новые объекты после проверки, считать их количество и энергопотребление, а также находить транспорт, подходящий для новичков.

1. Возможности программы

- добавление велосипеда, электровелосипеда, электросамоката, шлема или зарядной станции;
- проверка исправности объекта перед добавлением в парк;
- проверка корректности простоты управления транспортом;
- проверка энергопотребления электрических объектов;
- запрет пустых и повторяющихся инвентарных номеров;
- подсчёт общего количества объектов;
- подсчёт суммарного суточного энергопотребления;
- вывод транспорта, подходящего для новичков;
- вывод всех объектов парка.

2. Структура проекта

2.1 main.go

Точка входа в программу. Создаёт контейнер зависимостей и передаёт парк в консольное меню.

2.2 app/container.go

Собирает основные части приложения:

- создаёт сервисный центр FuncServiceCenter;
- передаёт его в Park;
- предоставляет готовый парк консольному слою.

Такой подход позволяет создавать зависимости в одном месте и не связывать консоль напрямую с реализацией проверки объектов.

2.3 console/menu.go

Содержит пользовательское меню и обработку консольного ввода.

Пользователь может:

1. завершить программу;
2. добавить новый объект;
3. узнать количество объектов в парке;
4. узнать суммарное энергопотребление;
5. получить список транспорта для новичков;
6. вывести все объекты.

При добавлении программа запрашивает тип объекта, инвентарный номер, состояние исправности, простоту управления и энергопотребление — в зависимости от выбранного типа.

2.4 domain/inventory.go

Описывает общие контракты и нетранспортные объекты.

- InvItem — общий интерфейс для всех объектов. Требует инвентарный номер, название и состояние исправности.
- EnergySpend — интерфейс для объектов, которые потребляют энергию.
- Helmet — шлем, для которого учитываются номер и исправность.
- EnergyStation — зарядная станция, дополнительно содержащая энергопотребление.

2.5 domain/transport.go

Описывает транспорт и его характеристики.

- Transport расширяет InvItem и добавляет оценку простоты управления.
- Bike представляет обычный велосипед.
- EBike представляет электровелосипед и реализует учёт энергопотребления.
- EScooter представляет электросамокат и также реализует учёт энергопотребления.

2.6 service/check.go

Содержит логику технической проверки объектов.

Интерфейс ServiceCenter задаёт контракт метода Check. Реализация FuncServiceCenter принимает объект только тогда, когда:

- объект не равен nil;
- объект исправен;
- простота управления транспортом находится в диапазоне от 1 до 10;
- энергопотребление объекта не является отрицательным.

2.7 service/park.go

Содержит основную бизнес-логику парка.

- AddItem проверяет объект и добавляет его, если инвентарный номер заполнен и не повторяется.
- TotalItems возвращает количество объектов.
- TotalEnergy суммирует энергопотребление всех объектов, реализующих EnergySpend.
- EasyTransport возвращает транспорт с оценкой простоты управления от 6 и выше.
- ShowAllItems возвращает копию списка объектов, чтобы внешний код не изменял внутреннее состояние парка напрямую.

3. Юнит-тесты

Тесты расположены в пакете service и используют стандартный пакет Go testing.

3.1 service/check_test.go

Проверяет работу технического осмотра FuncServiceCenter.

- TestCheckNil — объект со значением nil не проходит техосмотр.
- TestCheckWorkingItem — исправный шлем успешно проходит техосмотр.
- TestChecNotWorkingItem — неисправный шлем отклоняется.
- TestCheckEase — проверяет допустимые границы простоты управления: значения от 1 до 10 принимаются, остальные отклоняются.
- TestCheckEnergy — проверяет энергопотребление: отрицательное значение отклоняется, нулевое и положительное разрешаются.

Тесты TestCheckEase и TestCheckEnergy выполнены в табличном формате. Это позволяет проверить несколько входных значений одной тестовой функцией.

3.2 service/park_test.go

Проверяет правила добавления объектов в парк.

- TestParkRejectsWhenCheckFails — объект, не прошедший техосмотр, не добавляется; метод проверки вызывается один раз.
- TestParkAcceptsApprovedItem — одобренный электросамокат добавляется, а количество объектов увеличивается до одного.
- TestParkRejectsDuplicateNumber — объект с уже существующим инвентарным номером отклоняется.

Для изоляции тестов используется stubServiceCenter. Это тестовая реализация ServiceCenter, которая возвращает заранее заданный результат и считает количество вызовов метода Check.

4. Проделанная работа

- создана предметная модель транспортного парка;
- выделены отдельные интерфейсы для общих объектов, транспорта и потребителей энергии;
- реализованы пять типов объектов;
- создан сервис технической проверки;
- реализовано хранение и добавление объектов в парк;
- добавлена проверка уникальности инвентарных номеров;
- реализован подсчёт объектов и энергопотребления;
- реализован поиск транспорта для новичков;
- создано интерактивное консольное меню;
- зависимости приложения собраны в отдельном контейнере;
- написаны юнит-тесты для техосмотра и добавления объектов.

5. Dependency Injection и DI-контейнер

Dependency Injection используется при создании парка. Park не создаёт сервисный центр самостоятельно, а получает его извне.

5.1 app/container.go

Содержит простой ручной DI-контейнер Container и выступает точкой сборки приложения.

- создаёт реализацию проверки FuncServiceCenter;
- передаёт её в NewPark;
- сохраняет готовый Park в контейнере;
- не использует сторонний DI-фреймворк.

5.2 service/park.go

Функция NewPark(checker ServiceCenter) получает зависимость через параметр. Поэтому Park зависит от интерфейса, а не создаёт конкретный сервис проверки самостоятельно.

5.3 main.go

Создаёт контейнер один раз и передаёт готовый Park в консольное меню.

5.4 service/park_test.go

Реальный сервис проверки заменяется заглушкой stubServiceCenter. Это позволяет тестировать Park отдельно от настоящего техосмотра.

6. Применённые принципы SOLID

6.1 SRP — Single Responsibility Principle

Каждая часть программы выполняет отдельную задачу:

- console/menu.go взаимодействует с пользователем;
- service/check.go выполняет техническую проверку;
- service/park.go управляет объектами парка;
- domain содержит модели и интерфейсы предметной области;
- app/container.go собирает зависимости приложения;
- main.go только запускает программу.

Изменение правил техосмотра не требует менять меню, а изменение консольного интерфейса не затрагивает бизнес-логику парка.

6.2 OCP — Open/Closed Principle

Методы TotalEnergy и EasyTransport работают через интерфейсы EnergySpend и Transport. Новый тип транспорта или потребителя энергии можно добавить, реализовав нужный интерфейс, без изменения алгоритмов Park.

6.3 LSP — Liskov Substitution Principle

Bike, EBike и EScooter могут использоваться в любом месте, где ожидается Transport. Helmet и EnergyStation могут использоваться через общий интерфейс InvItem. Методы парка не зависят от конкретного типа объекта и работают с его контрактом.

6.4 ISP — Interface Segregation Principle

Вместо одного большого интерфейса используются несколько небольших:

- InvItem содержит возможности, общие для всех объектов;
- Transport добавляет только простоту управления;
- EnergySpend добавляет только энергопотребление.

Поэтому шлем не обязан реализовывать энергопотребление, а зарядная станция — простоту управления.

6.5 DIP — Dependency Inversion Principle

Park зависит от абстракции ServiceCenter, а не от конкретного FuncServiceCenter. Конкретная реализация выбирается в app/container.go и передаётся в парк извне. В тестах та же абстракция позволяет подставить stubServiceCenter.

7. Применённые принципы GRASP

7.1 Information Expert

Логика размещена рядом с данными, необходимыми для её выполнения:

- транспорт самостоятельно возвращает название, номер, исправность и простоту управления;
- электрические объекты самостоятельно возвращают своё энергопотребление;
- Park хранит коллекцию объектов, поэтому именно он считает их количество, общую энергию и формирует выборки.

7.2 Controller

Функция Run в console/menu.go принимает команды пользователя и вызывает соответствующие методы Park. При этом она не выполняет правила техосмотра и учёта самостоятельно.

7.3 Creator

- app.Container создаёт FuncServiceCenter и Park, потому что отвечает за сборку приложения;
- функция addItem создаёт предметные объекты из введённых пользователем данных.

7.4 Low Coupling

Связность снижена использованием интерфейсов:

- Park не знает конкретную реализацию сервисного центра;
- подсчёт энергии не зависит от конкретных типов электрических объектов;
- выбор простого транспорта не зависит от велосипеда или самоката напрямую.

7.5 High Cohesion

Связанные операции собраны вместе:

- модели находятся в domain;
- проверка находится в service/check.go;
- управление коллекцией находится в service/park.go;
- консольный ввод и вывод находятся в console/menu.go.

7.6 Polymorphism

Полиморфизм применяется в TotalEnergy, EasyTransport, ShowAllItems и FuncServiceCenter.Check. Код определяет возможности объекта через интерфейсы, а не через перечисление всех конкретных типов.

7.7 Protected Variations

Интерфейс ServiceCenter защищает Park от изменений способа технической проверки. Реализацию можно заменить, не меняя код парка. Интерфейсы Transport и EnergySpend аналогично защищают алгоритмы парка от появления новых типов объектов.

7.8 Pure Fabrication

FuncServiceCenter и Container не являются физическими объектами транспортного парка, но введены для разделения обязанностей: первый инкапсулирует проверку, второй собирает зависимости.

8. Другие принципы разработки

8.1 KISS — Keep It Simple, Stupid

Проект использует простые решения:

- данные хранятся в обычном срезе;
- зависимости передаются через конструктор;
- интерфейсы небольшие;
- для разных типов объектов не используется сложная иерархия;
- DI реализован вручную без дополнительного фреймворка.

Для текущего учебного проекта не используются база данных, сложная конфигурация и отдельная библиотека внедрения зависимостей.

8.2 DRY — Do Not Repeat Yourself

Общие правила собраны в одном месте:

- проверка всех объектов сосредоточена в FuncServiceCenter.Check;
- добавление и проверка уникальности выполняются только в Park.AddItem;
- подсчёт энергии реализован один раз через EnergySpend;
- логика выбора транспорта реализована один раз через Transport;
- тест TestCheckEase использует табличный подход вместо отдельных тестовых функций для каждого значения;
- тест TestCheckEnergy аналогично объединяет несколько сценариев в одну таблицу.

Методы Name, InvNum и IsWorking повторяются у моделей намеренно: каждый тип явно реализует интерфейс Go и самостоятельно описывает своё поведение.

8.3 YAGNI — You Are Not Gonna Need It

В проект не добавлены возможности, которые не требуются текущей задаче:

- база данных;
- удаление и редактирование объектов;
- сетевой API;
- конфигурационные файлы;
- сложная система регистрации зависимостей.

Реализованы только необходимые операции учёта.

8.4 SoC — Separation of Concerns

Проект разделён на независимые области:

- domain — предметные модели и контракты;
- service — бизнес-правила;
- console — пользовательский интерфейс;
- app — сборка зависимостей;
- main.go — запуск приложения.

8.5 Encapsulation

Поля items и checker структуры Park закрыты от внешнего кода. Доступ к данным выполняется через методы. ShowAllItems возвращает копию среза, поэтому внешний код не может напрямую заменить элементы внутреннего списка парка.

8.6 Composition over Inheritance

В Go поведение собирается через композицию интерфейсов. Например, Transport включает контракт InvItem, а электрический транспорт отдельно реализует EnergySpend. Наследование классов не используется.

9. Запуск

Для запуска приложения:

go run .

Для запуска всех юнит-тестов:

go test ./...
